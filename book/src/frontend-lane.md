# The Frontend Lane: Elaboration-Accept Hierarchies

The [microdesign lane](microdesign-lane.md) checks a downstream tool's
constant resolution inside one module. The frontend lane raises the
stakes to the part of a frontend that is genuinely hard to get right:
**elaboration across module boundaries**. Parameter defaults flowing
through instance bindings, package-qualified names resolved from
another scope, generate conditions whose truth depends on all of the
above — this is where parsers and elaborators hide their bugs, because
every fact depends on facts computed somewhere else.

Like its sibling, the lane is oracle-backed: the builder evaluates
every parameter, every binding, and every generate predicate *as the
hierarchy is constructed*, then emits two projections of that single
evaluated IR — an **un-elaborated** `.sv` (everything symbolic) and a
JSON manifest of the facts a correct elaboration must reproduce. No
re-parse, no bundled elaborator; the builder is the oracle.

## Generating one artifact

Two scoped knobs shape the hierarchy: `--lane-n-params` (default 5)
sets the top module's parameter count, `--lane-n-children` (default 2)
the number of child instances:

```bash
cargo run --release -- --artifact frontend --seed 0 --lane-n-params 4 --lane-n-children 2
```

The SystemVerilog goes to **stdout**:

```systemverilog
// Generated by anvil frontend (Phase 8). Top: acc_0
package acc_0_pkg;
    localparam int K = 1;
endpackage

module child_0 #(
    parameter int CP0 = 24,
    parameter int CP1 = 17,
    parameter int CP2 = 23,
    parameter int CP3 = 7
);
endmodule

module acc_0 #(
    parameter int P0 = 57,
    parameter int P1 = 38,
    parameter int P2 = 36,
    parameter int P3 = 54
);
    localparam int L0 = (P0 - 4);
    localparam int L1 = (L0 + 4);
    localparam int L2 = (L1 - 3);
    localparam int L3 = (L2 + 4);
    child_0 #(
        .CP0((P0 + 0)),
        .CP1((P1 + 2)),
        .CP2((P2 + 2)),
        .CP3((P3 + 3))
    ) u_0_0 ();
    child_0 #(
        .CP0((P0 + 3)),
        .CP1((L1 + 2)),
        .CP2((P2 + 2)),
        .CP3((P3 + 1))
    ) u_0_1 ();
    generate
        if ((P0 >= acc_0_pkg::K)) begin : g_taken
            logic gflag;
            assign gflag = 1'b1;
        end else begin : g_else
            logic gflag;
            assign gflag = 1'b0;
        end
    endgenerate
endmodule
```

Every part of that shape is deliberate:

- **Child modules are parameterized stubs** — declared parameters, no
  body. Behavioural code would only cloud the target; here the *whole*
  artifact is elaboration surface.
- Each instance **overrides every child parameter with an expression**,
  never a literal. `.CP1((L1 + 2))` forces a tool to resolve the
  top-scope localparam chain `L0 → L1` *before* it can bind a child
  parameter. The two instances bind different expressions to the same
  child, so per-instance resolution is observable rather than shared.
- The **generate predicate crosses a package boundary**
  (`P0 >= acc_0_pkg::K`), tying scope resolution and constant
  evaluation into one branch decision.

Note also that the child stubs are declared *before* the top module —
the top is not the first `module` in the file. Anything downstream that
assumes "first declaration = top" gets this artifact wrong.

## The elaborated-facts manifest

The manifest goes to **stderr**, or to a file beside the `.sv` when
`--out` is set. Abbreviated, for the run above:

```json
{
  "seed": 0,
  "top": "acc_0",
  "packages": [
    { "name": "acc_0_pkg", "constants": { "K": 1 } }
  ],
  "top_params": {
    "P0": { "value": 57, "expr": "57" }
  },
  "top_localparams": {
    "L0": { "value": 53, "expr": "(P0 - 4)" },
    "L1": { "value": 57, "expr": "(L0 + 4)" }
  },
  "instances": [
    {
      "inst_name": "u_0_0",
      "child_module": "child_0",
      "resolved_bindings": { "CP0": 57, "CP1": 40, "CP2": 38, "CP3": 57 }
    },
    {
      "inst_name": "u_0_1",
      "child_module": "child_0",
      "resolved_bindings": { "CP0": 60, "CP1": 59, "CP2": 38, "CP3": 55 }
    }
  ],
  "generate_branches": {
    "g_taken": { "taken": true }
  }
}
```

The load-bearing category is `instances[*].resolved_bindings`: for each
instance, the value each child parameter must hold after its binding
expression is evaluated *in the parent's scope*. A tool that resolves
`u_0_1`'s `CP1` to anything but `59` has mis-handled either the
`L0 → L1` localparam chain or the binding itself — and the manifest
says so without running a single simulation cycle.

## Writing to a directory

With `--out`, both files are named after the **top** module:

```bash
cargo run --release -- --artifact frontend --seed 0 --lane-n-params 4 --lane-n-children 2 --out ./fe-corpus
ls ./fe-corpus
```

```text
acc_0.json
acc_0.sv
```

The stem comes from the builder's own top name — not from the order
modules appear in the emitted text, which would name these files after
the first child stub.

## Reproducibility

The same contract as every lane: one `ChaCha8Rng::seed_from_u64(seed)`,
no wall-clock, no thread nondeterminism. A fixed
`(seed, --lane-n-params, --lane-n-children)` triple yields
byte-identical SV *and* manifest on any machine, forever.

## How the lane is kept honest

`tests/frontend_parity.rs` carries the proofs, in the same three
layers as its sibling:

- **Agreement** — the hierarchy-aware comparator agrees with a
  synthetic tool report derived from the oracle itself.
- **Perturbation (the real proof)** — one test per fact category flips
  a single fact and asserts the comparator *catches* it: top
  parameters, top localparams, package constants, **per-instance
  bindings**, generate branches, instance presence on either side, and
  seed/top disagreement. Agreement alone would be vacuous if the
  comparator could not fail.
- **Real tools** — three `#[ignore]`-gated gates (so a tool-less
  `cargo test` stays green) run the generated corpus through real
  frontends: Yosys hierarchy `write_json`, a generic downstream
  elaborator, and Verilator's JSON AST
  (`--json-only`/`--json-only-output`, which skips with an explicit
  message on a Verilator build lacking those flags rather than
  silently passing).

As with every non-DUT lane, the generator path (`src/frontend/`) is
sealed off from the DUT lane. It reuses the microdesign lane's
`ConstExpr` algebra, evaluator, and SV expression printer, so the two
oracle lanes cannot drift apart at the expression layer — a fix in one
is a fix in both.

Why this matters beyond ANVIL's own gates: frontends accumulate
grammar and elaboration corner-cases that acceptance testing never
reaches, because "it parsed" and "it parsed and resolved everything
correctly" are different claims. Shipping the expected facts *with*
each artifact is what turns the first into the second.

## Driving it from an agent

Over MCP, `generate` and `introspect` take `lane: "frontend"` with the
scoped `n_params` / `n_children` knobs, and each artifact's manifest is
served as a resource beside its SV. See
[API Reference: Tools](api-tools.md) and the lanes catalog in
[API Reference: Resources & Prompts](api-resources-prompts.md).
