# The Microdesign Lane: Oracle-Backed Const-Expr Artifacts

The default DUT lane asks one question of a downstream tool: *does it
accept legal, unusual, synthesizable RTL?* Acceptance is a strong bar,
but it is a one-bit answer. A frontend can parse a module, elaborate
it, report success — and still have resolved a `localparam` to the
wrong value. Nothing in an acceptance run would notice.

The microdesign lane exists for exactly that gap. It is deliberately
the *opposite* of the DUT lane: instead of structurally rich RTL with
no semantic oracle, it emits a tiny, self-contained `.sv` whose
elaboration facts are **known by construction**, and ships those facts
beside the artifact as a machine-checkable JSON manifest. A downstream
parser or elaborator can then be checked *against an oracle* — not
"did it fail to error," but "did it resolve every parameter, width,
and generate branch to exactly the value the builder computed."

There is no analysis pass and no bundled elaborator behind this. The
generator builds a typed dependency DAG of integer constant
expressions and evaluates each node *as it is built*, so the builder
itself is the oracle. The emitted SystemVerilog keeps every expression
symbolic; the manifest records what elaboration must resolve them to.
Both are projections of the same evaluated in-memory IR, so they
cannot drift apart.

## Generating one artifact

Select the lane with `--artifact microdesign`. One scoped knob,
`--lane-n-params` (default 5), sets how many parameter / localparam
declarations the module carries:

```bash
cargo run --release -- --artifact microdesign --seed 7 --lane-n-params 5
```

The SystemVerilog goes to **stdout**:

```systemverilog
// Generated by anvil microdesign (Phase 7). Module: mc_7
package mc_7_pkg;
    localparam int K = 8;
endpackage

module mc_7 #(
    parameter int P0 = 9,
    parameter int P3 = (P0 - 6),
    parameter int P4 = (P3 - 4)
);
    localparam int P1 = (P0 * 3);
    localparam int P2 = ((P0 >= 4) ? P1 : 8);
    localparam int PKG_REF = mc_7_pkg::K;
    localparam int W_SIG = (((P4 % 8) + 8) % 8 + 1);
    logic [W_SIG-1:0] sig;
    assign sig = '0;
    generate
        if (P0 >= 8) begin : g_taken
            logic gflag;
            assign gflag = 1'b1;
        end else begin : g_else
            logic gflag;
            assign gflag = 1'b0;
        end
    endgenerate
endmodule
```

Notice what the text does *not* contain: resolved numbers. `P3` is
declared as `(P0 - 6)`, the signal width as `[W_SIG-1:0]`, the generate
condition as `P0 >= 8`. Resolving those is the downstream tool's job —
that is the surface under test. The artifact concentrates the
constructs a frontend has to get right:

- **overridable `parameter`s** whose defaults reference earlier
  parameters;
- **derived `localparam` chains**, including a ternary;
- a **package-qualified constant** (`mc_7_pkg::K`) referenced across a
  scope boundary;
- a **width expression** used in a declaration. The
  `(((P4 % 8) + 8) % 8 + 1)` shape is doing real work here: `P4`
  resolves to `-1`, and SystemVerilog's `%` takes the sign of its left
  operand, so the doubled modulo is what normalizes the result back
  into `0..7`. A tool that treats `%` as a Euclidean remainder gets a
  different width and is caught;
- a **generate `if`** whose taken branch depends on a parameter.

## The expected-facts manifest

The manifest goes to **stderr** — so stdout pipelines stay clean — or
to a file beside the `.sv` when `--out` is set. Abbreviated, for the
run above:

```json
{
  "seed": 7,
  "top": "mc_7",
  "params": {
    "P0": { "value": 9,  "expr": "9" },
    "P3": { "value": 3,  "expr": "(P0 - 6)" },
    "P4": { "value": -1, "expr": "(P3 - 4)" }
  },
  "localparams": {
    "P1": { "value": 27, "expr": "(P0 * 3)" },
    "P2": { "value": 27, "expr": "((P0 >= 4) ? P1 : 8)" }
  },
  "widths": {
    "sig": { "msb": 7, "lsb": 0, "bits": 8 }
  },
  "generate": {
    "g_taken": { "taken": true }
  },
  "package_constants": {
    "mc_7_pkg::K": 8
  }
}
```

Every category is a claim about what a correct elaboration must
conclude: each parameter's resolved value (beside its symbolic
`expr`), each localparam's, each declared signal's resolved
`msb`/`lsb`/`bits`, which generate branch is taken, and each package
constant's value. A `const_exprs` array (omitted above) additionally
lists every expression with its value and the minimum bit-width that
holds it — negative values report width `1`, since widths in the
artifact are always driven by non-negative results.

To check a tool: elaborate the `.sv`, extract the tool's resolved view
of those same facts, and compare. A mismatch is a real finding in one
of the two — and since the oracle is a few dozen lines of `i128`
arithmetic evaluated at construction time, the odds favour the tool
being wrong.

## Writing to a directory

With `--out`, both projections land as files named after the top
module:

```bash
cargo run --release -- --artifact microdesign --seed 7 --lane-n-params 5 --out ./md-corpus
ls ./md-corpus
```

```text
mc_7.json
mc_7.sv
```

The filename stem is the lane builder's own top name (`mc_<seed>`) —
the same name the manifest's `top` field carries, by construction.

## Reproducibility

The lane keeps the project-wide contract: one
`ChaCha8Rng::seed_from_u64(seed)`, no wall-clock, no thread
nondeterminism. The same `(seed, --lane-n-params)` pair produces
byte-identical SV *and* a byte-identical manifest, on any machine,
forever. A bug report is therefore two numbers, not an attachment.

## How the lane is kept honest

`tests/microdesign_parity.rs` carries the proofs, in three layers:

- **Agreement** — the comparator agrees with a synthetic tool report
  derived from the oracle itself
  (`comparator_agrees_on_synthetic_tool_report_built_from_the_oracle`).
- **Perturbation (the real proof)** — a dedicated test per fact
  category flips one fact and asserts the comparator *catches* it:
  parameters, localparams, widths, generate branches, package
  constants, facts missing on either side, and seed/top disagreement.
  Agreement alone would be vacuous if the comparator could not fail.
- **Real tools** — `parity_against_real_yosys_write_json` (marked
  `#[ignore]`, so a tool-less `cargo test` stays green) elaborates the
  generated corpus with Yosys and compares its `write_json` output
  against the manifest through a *scoped* comparator. Scope matters:
  tools expose different fact subsets — Yosys folds `localparam`s and
  package constants into their use sites, which
  `yosys_scope_ignores_localparams_and_package_constants` pins
  explicitly rather than leaving as a silent gap.

The lane is also sealed off from the DUT lane: it is a separate
generator path (`src/microdesign/`), never invoked from the DUT
generate path, so enabling it cannot perturb DUT output. The
umbrella's per-lane byte-identical regression proofs hold that line.

## Driving it from an agent

Everything above is reachable over MCP: the `generate` and
`introspect` tools take `lane: "microdesign"` plus the scoped
`n_params` knob, and the artifact's manifest is served as a resource
beside its SV. See [API Reference: Tools](api-tools.md) and the lanes
catalog in
[API Reference: Resources & Prompts](api-resources-prompts.md).

The sibling [frontend lane](frontend-lane.md) (`--artifact frontend`)
extends this idea to hierarchies, where *cross-module* elaboration
becomes the pressure point.
